# Legacy Blockly compatibility samples

`legacy-builtins-project.xml` covers the project restore path with `controls_if` (elseif/else), `math_number_property` (DIVISIBLE_BY), `math_on_list` (MODE), `text_charAt` (LAST/no AT input), `text_join` (three items), plus logic comparison/ternary and a flow statement.

`legacy-builtins-backpack.json` covers the backpack restore path for the three Blockly mutators beyond `controls_if` and `text_join`, and a three-item `text_join`. Restore each item from an otherwise minimal project to verify that the full builtin pack is loaded on demand.

Expected checks: all saved inputs and dropdown values remain present after restore and reload; changing the relevant dropdown updates inputs/checks; flow statements outside a loop show the Blockly warning; restored backpack items leave the backpack only after a successful restore.

## Large synthetic restore sample

`legacy-large-synthetic-project.xml` is generated from the compatibility cases above plus old `if_block`, `switch_block`, and variadic string blocks. It contains 600 repeated top-level fixtures (601 including the fixed `cpp_main` root), three named Blockly variable models, and references from arithmetic/comparison blocks. `legacy-large-synthetic-backpack.json` includes the legacy and builtin mutator shapes plus a reference to the synthetic `count` variable. This is reproducible load data, not a captured user project.

The same generator also creates `legacy-large-nested-synthetic-project.xml`. It is a synthetic, connected program assembled from real application and Blockly block types: nested `for_block`, `controls_if`, legacy `if_block`, `switch_block`, `cout_block`, mutating text operations, arithmetic/comparison blocks, and variable references. It uses no benchmark-only wrapper types. The control-flow depth and repetition are generated data, so this is more representative than the earlier wrapper chain but is still not a captured user project.

Regenerate it with `node scripts/generate-legacy-restore-fixture.mjs 600` (valid range: 50–5000). Start the normal Vite dev server and open `/scripts/legacy-restore-benchmark.html` to compare one-shot restore against frame-batched root creation at several roots per frame. The page reports total restore time, longest synchronous chunk, frame gaps, and structural checks for mutator shapes, variable ids, and backpack restoration. It does not change the app's production restore behavior. The measurements are browser/device-specific and synthetic; use only batch sizes that pass the consistency checks.

Calibration (600 generated fixtures, 1,804 total blocks, two runs per mode): visible one-shot restore took 330–366 ms synchronously; parsing the same XML into a headless workspace took 32–39 ms and preserved the block/variable profile. `Blockly.Xml.domToBlockHeadless` is not exposed by this Blockly build. Switching a visible workspace's `rendered` flag off and back on is invalid: Blockly then treats it as headless and rejects SVG block creation.

The safer adaptive prototype keeps each root atomic and fills frames up to 6/10/14 ms budgets. All variants preserved the mutators, three variables and 162 references, and all five backpack items. Total restore took 3.93–4.44 s; individual roots took 41–65 ms, and maximum observed frame gaps were 56–122 ms. A large root can exceed the budget by itself, so adaptive scheduling reduces neither worst-case task length nor frame gaps enough to justify production rollout. The lower headless parse time points to SVG/render work as the major remaining cost, but moving a headless model into a visible workspace still needs a supported, consistency-checked path.

Resize API comparison (same fixture, two runs, 10 ms target slice): leaving resizing enabled during per-root `domToBlock` calls took 2.53–3.98 s. Disabling resizes for each frame slice with the public `WorkspaceSvg.setResizesEnabled(false/true)` took 0.90–0.93 s; the longest slice was 13.5–14.2 ms and maximum frame gaps were 30–32 ms. Disabling resizes for the full restore took 1.11–1.18 s, with an 83 ms maximum frame gap. All variants preserved mutators, variables and backpack items. However, the current app uses one `Blockly.Xml.domToWorkspace` call, and Blockly already disables resizes for that entire call. The synthetic file also has 601 top-level roots, unlike a typical project whose program is nested under one main block. These results justify retaining resize batching for future multi-root scheduling experiments, but not replacing the current production restore path.

Nested-workspace comparison using the application-shaped fixture (2 runs, 3,065 blocks in one `cpp_main` tree, including eight nested loops and 120 each of the major conditional/mutator shapes): visible one-shot XML restore took 0.90–1.40 s, while headless creation took 0.10–0.12 s. Instrumenting the visible restore recorded 6,697 `initSvg` calls (137.4 ms total), 3,065 renderer `render` calls (359.9 ms total), and 1,460 `resizeContents` calls (1.1 ms total). Renderer cost remains hundreds of milliseconds and workspace resize remains negligible, consistent with the previous nested synthetic sample's qualitative result; instrumentation varies between runs and its per-call totals are diagnostic, not additive wall-clock values. Mutator shapes (120 each for builtin if, legacy if, switch, text join, and legacy variadic string), three variable models/376 references, and all five backpack items restored consistently in visible, headless, and staged prototypes. The 10 ms root scheduler still cannot subdivide this one connected root: longest synchronous calls were 0.80–1.02 s, with total staged time about 1.12–1.41 s. All results are synthetic and cannot substitute for a captured older user project.

Repeated renderer composition comparison (Blockly 12.5.1, same in-app browser session): each profile records the first XML restore after module load, does three warmup restores, then measures seven steady restores and three instrumented restores. “Cold” here means first XML restore after Blockly has loaded; it excludes page startup and network transfer. `control` (3,065 blocks): cold 0.97 s, steady median 0.68 s (0.61–0.82 s), renderer median 347 ms (323–398 ms; 0.113 ms/block). `text` (2,705 blocks): cold 0.91 s, steady median 0.58 s (0.50–0.67 s), renderer median 258 ms (236–279 ms; 0.095 ms/block). `mixed` (2,885 blocks): cold 0.90 s, steady median 0.71 s (0.59–0.81 s), renderer median 347 ms (303–374 ms; 0.120 ms/block). Resize work remained below 1 ms in the three instrumented repeats. All three profiles passed direct and headless structural, mutator, variable-reference, and backpack checks; the prior two-run staged prototypes also passed. Cold XML restore is consistently slower than warmed restore, and per-block renderer time still varies with composition. The conclusion remains that renderer work is substantial while resize work is negligible, not that all blocks have equal rendering cost. Repeat with `/scripts/legacy-restore-benchmark.html?fixture=control&steady`, `?fixture=text&steady`, or `?fixture=mixed&steady` in the same browser.

Renderer API assessment (Blockly 12.5.1): its `BlockSvg.queueRender()` exists in the installed type declarations but is explicitly annotated `@internal`; the render-management queue controls are similarly internal. `BlockSvg.render()` remains synchronous. Blockly's supported custom renderer extension point lets applications alter block measurement and drawing, but its documented purpose is visual customization and it does not provide a supported way to pause and incrementally flush XML restore rendering. We therefore avoid replacing `queueRender` or patching renderer internals. See [BlockSvg API](https://docs.blockly.com/reference/classes/BlockSvg/), [WorkspaceSvg API](https://docs.blockly.com/reference/classes/WorkspaceSvg/), [custom renderer guide](https://docs.blockly.com/guides/create-custom-blocks/renderers/create-custom-renderers/basic-implementation/), and [render management guide](https://docs.blockly.com/guides/contribute/core/core-architecture/render-management/).
